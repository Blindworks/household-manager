Feature branch `feature/haushaltskalender` builds a household calendar with recurring events (RRULE).

## Entity / dependency (Task 2, done)
- `org.dmfs:lib-recur:0.17.1` resolves cleanly and has the full API the later `RecurrenceExpansionService` needs: `RecurrenceRule(String)` + `InvalidRecurrenceRuleException`, `RecurrenceRule.iterator(DateTime)`, `RecurrenceRuleIterator.hasNext()/nextDateTime()/fastForward(DateTime)`, `org.dmfs.rfc5545.DateTime`. Verified via `javap` against the actual jar, not just javadoc — worth doing again if the version ever changes.
- `CalendarEvent` (`model/entity/CalendarEvent.java`) stores EXDATEs as a comma-joined `TEXT` column (`exdates`), parsed on demand via `exdateSet()`/written via `addExdate()`. `CalendarCategory` enum is a fixed list (GENERAL/FAMILY/HEALTH/HOUSEHOLD/WORK/BIRTHDAY) - frontend owns colors/labels.
- `CalendarEventRepository` lives in `com.household.manager.repository` per [[jpa-repository-package]] constraint.

## RecurrenceExpansionService (Task 3, done)
- `RecurrenceExpansionService` (`backend/src/main/java/com/household/manager/calendar/`) is confirmed as the sole lib-recur touchpoint: public API is `validate(String)` and `expand(String rrule, LocalDate seriesStart, LocalDate from, LocalDate to) -> List<LocalDate>` — no `DateTime` in any public signature.
- Verified empirically (compiled+ran a standalone probe against the real 0.17.1 jars, not just javap signatures) before trusting the design-doc draft: `org.dmfs.rfc5545.DateTime(int year, int month, int day)` is **0-based month** like `java.util.Calendar` (month=6 → July) — confirmed via `RecurrenceRuleIterator` output on a real BYDAY=TU rule, not just javadoc (javadoc text alone doesn't say which convention). Conversion `getMonthValue() - 1` / `getMonth() + 1` at the `LocalDate`↔`DateTime` boundary is correct.
- `RecurrenceRuleIterator.fastForward(DateTime)` is **inclusive** of the target date — after `fastForward(X)`, `nextDateTime()` returns X itself if X is an occurrence, not the next one after it. Relevant for expand()'s window-start handling.
- `new RecurrenceRule("FREQ=BANANA")` throws `InvalidRecurrenceRuleException` with message "FREQ part is missing" (unrecognized FREQ value is treated as absent, not as an enum-parse error) — still catchable the same way.
- Lesson reinforced: for a brittle third-party API, a quick standalone `javac`+`java` probe against the actual jar (not just `javap` signatures or javadoc prose) is worth the few minutes — it directly answers the question javap/javadoc can't (0-based vs 1-based month, fastForward inclusivity) before committing to an implementation.
- Code review caught a silent-cap risk: hitting `MAX_OCCURRENCES` produced no signal, so a syntactically-valid-but-wrong rule (e.g. accidental `FREQ=HOURLY`) would silently drop occurrences from a month view with nothing to grep for. Fixed by mirroring the exact pattern already used in `WasteCalendarIcsParser.collectOccurrences` (`log.warn` only when the cap — not the window end or series end — is what stopped the loop; message includes the raw rule string for diagnosability). **Rule going forward:** any loop with a hard safety cap (`MAX_OCCURRENCES`-style) needs a warn log gated on "did the cap actually fire", not on every loop exit — check this project's other capped loops (grep `MAX_OCCURRENCES\|guard++`) for the same gap before assuming a new one is fine.
- Also verified via probe (not guessed): `new RecurrenceRule(null)` throws `IllegalArgumentException` ("recur must not be null"), `new RecurrenceRule("")`/`"   "` throw `InvalidRecurrenceRuleException` ("FREQ part is missing") — both already covered by the existing `InvalidRecurrenceRuleException | IllegalArgumentException` catch, so `validate(null/""/"   ")` needed only regression tests, no code change.

## Lesson: defensive parsing behind a public Lombok setter
Code review caught that `exdateSet()` split a comma-joined string and called `LocalDate::parse` directly on each token, with no filter for empty tokens. Even though *today* only `addExdate()` (which always produces a clean, sorted, deduped string) writes to the field, the entity has a public `@Setter` (from class-level `@Setter`/`@Data`-style Lombok), so any future writer (CSV import, manual DB fix, DTO mapping) can put in a trailing/double comma and blow up parsing with an uncaught `DateTimeParseException`.
**Rule going forward:** when parsing a delimiter-joined string field that sits behind a public setter (not just a private/internal-only field), always filter empty tokens after `split(",")` before calling a throwing parser (`LocalDate::parse`, `Integer::parseInt`, etc.) - don't rely on "only my own writer method touches this" as a safety argument, because Lombok's generated setter is also a writer.
This pattern likely recurs anywhere else in the codebase that stores a delimited list in a TEXT column (grep for `.split(",")` before assuming a similar field is safe).

Task list (from `docs/superpowers/specs/` under this feature) proceeds in small dependency-ordered steps (entity -> service -> controller -> frontend); each step gets its own review with a code-quality pass that has caught real issues (this one) - expect that pass to run on every subsequent task too.

## CalendarEventService CRUD (Task 4, done) - review fixes
- **RRULE change on `update()` must orphan-proof exdates/overrides.** The plan's first-draft `update()` just called `applyRequest` and saved — it never compared old vs. new `rrule`. Fixed semantics (read the *old* `rrule` from the loaded entity **before** `applyRequest` overwrites it, compare against the normalized new value with `Objects.equals`): if the RRULE string changes at all (including being removed or newly set), `exdates` is set to `null` and `repository.deleteByRecurringParentId(id)` runs — old override rows/EXDATEs are bound to the old rule and aren't meaningfully mappable to a new one (matches common calendar-app behavior). If the RRULE is unchanged (e.g. only the title changes), exceptions are left alone. This is the load-bearing rule for any future occurrence/override work in Task 5/6 — don't let a refactor of `update()` silently drop this comparison.
- **`endDate` is allDay-only.** `applyRequest` originally set `event.setEndDate(request.getEndDate())` unconditionally, contradicting the entity Javadoc ("nur fuer mehrtaegige ganztaegige Termine"). Fixed to `request.isAllDay() ? request.getEndDate() : null`, mirroring the existing `startTime`/`endTime` allDay-null pattern right above it.
- **Title length must be validated in the service, not left to the DB.** Column is `varchar(200) not null`; without an explicit check a 201+ char title passed `validate()` and failed at `save()` as an opaque 500. Added a post-trim `length() > 200` check in `validate()` with a German message — same pattern as the other `ResponseStatusException(BAD_REQUEST, "...")` checks in that method.
- General lesson: when a plan document ships literal code for a service, still sanity-check it against the entity Javadoc/column constraints and against "what happens to already-existing rows on a state transition" (create-only tests don't exercise the update-mutates-existing-relationships path) — both gaps here were exactly that kind of thing unit tests for `create()` alone would never surface.

## Occurrence-Operationen (Task 6, done)
- `deleteOccurrence(id, date)` / `updateOccurrence(id, date, request)` added to `CalendarEventService` exactly as drafted in the plan — no deviation needed this time; all 4 planned tests passed on first implementation attempt (32 tests total in `CalendarEventServiceTest` after appending: 28 pre-existing + 4 new, all green).
- Key invariants carried forward from Task 4's RRULE-orphan lesson: `updateOccurrence` must call `override.setRrule(null)` **after** `applyRequest(request, override)` (not before — `applyRequest` sets `rrule` from the request, so the null-out has to come last) so an override row can never itself define a series. `deleteOccurrence` on a series must delete any existing override for that occurrence date *before/alongside* adding the EXDATE, or the override row is orphaned (no code references it, but it's still a live DB row that would show up in `getOccurrences`' `findAll()` scan since nothing filters out overrides whose parent has an EXDATE for that date — the delete is the only thing preventing that ghost row).
- `updateOccurrence` rejects single (non-recurring) events with a 400 `ResponseStatusException` — occurrence-level edits only make sense for series; single events are edited via the plain `update(id, request)` path.

## Occurrence-Operationen — Quality-Review-Nachbesserung (post-Task 6)
Review nach Task 6 fand echte Bugs, weil die Leseseite (`getOccurrences`) Overrides ausschliesslich ueber ihr eigenes `startDate` rendert, unabhaengig vom Master:
- **`isOverride()` muss vor `isRecurring()` geprueft werden** in `deleteOccurrence`. Eine Override-Zeile hat `rrule == null` (von `updateOccurrence` bewusst genullt), also ist `isRecurring()` fuer sie *immer* false. Ohne den Check zuerst laeuft die Loeschung einer Override-Id in den Einzeltermin-Zweig, loescht nur die Zeile — und die Serie zeigt an dem Tag wieder das unbearbeitete Original, weil kein EXDATE am Master gesetzt wurde. Fix: bei `isOverride()` den Master laden, dort `addExdate(event.getRecurrenceDate())`, dann die Override-Zeile loeschen.
- **`updateOccurrence` muss das Zieldatum gegen `expansionService.expand(rrule, seriesStart, date, date)` pruefen** (leer = kein echtes Vorkommen → 400), sonst laesst sich ein Override auf ein Datum ausserhalb der Serie anlegen — ein Phantom-Termin, der dauerhaft in jeder Fensterabfrage auftaucht, weil `getOccurrences` Overrides unabhaengig vom Master rendert.
- **Override gewinnt gegenueber EXDATE:** `updateOccurrence` muss ein bestehendes EXDATE fuers Zieldatum entfernen (`master.removeExdate(occurrenceDate)`, neue Methode analog zu `addExdate`, setzt `exdates` auf `null` statt leerem String wenn nichts uebrig bleibt) — sonst waere ein Datum gleichzeitig "geloescht" und "geaendert".
- **`deleteOccurrence` bei Einzelterminen muss das uebergebene Datum gegen `startDate` pruefen** (400 bei Mismatch) — sonst loescht ein falsches/veraltetes Client-Datum still den ganzen Termin.
- **`updateOccurrence` muss `request.setRrule(null)` setzen, bevor `validate(request)` laeuft**, nicht erst danach — sonst schlaegt eine im Formular versehentlich mitgeschickte (evtl. ungueltige) Master-RRULE die Validierung fehl, obwohl sie fuer Overrides ohnehin verworfen wird.
- Alle 7 Nachbesserungs-Tests liessen sich rein mit Mockito-Mocks abbilden, auch der Interaktionstest "Override anlegen, dann Serien-RRULE per `update()` aendern → Override weg" (prueft nur, dass `deleteByRecurringParentId` feuert — echte Persistenz zwischen den beiden Service-Aufrufen wird vom Mock nicht simuliert, reicht aber, weil dieser Cleanup-Pfad bereits in Task 4 verifiziert ist).
- **Lesson:** Bei jeder neuen Zeilenart, die eine bestehende Boolean-Ableitung (`isRecurring()`) zu einem unerwarteten Wert fuehrt (hier: Override-Zeile → immer `false`), explizit durchspielen, welcher Code-Zweig fuer diese Zeilenart *tatsaechlich* greift — nicht nur fuer die Zeilenart, fuer die die Methode urspruenglich geschrieben wurde. Gleiches Muster wie bei Task 4s RRULE-Orphan-Bug: state-transition-Effekte auf *andere* Zeilen/Objekte sind der typische blinde Fleck von Create-only-Tests.

## Task 8: CalendarReminderScheduler + EntitySource.CALENDAR (done) — DST-Bug in der Quality-Review

`CalendarReminderScheduler` (`backend/src/main/java/com/household/manager/calendar/`) feuert `event.calendar_reminder` in den Entity-State-Layer (`EntityStateService.reportEvent`); `EntitySource.CALENDAR` vor `MANUAL` ergänzt. Erstversion (`lastChecked` als `LocalDateTime` in Wandzeit, Fenster `(since, until]`) hatte 3 Tests grün, aber die Quality-Review fand einen echten Bug plus zwei Lücken:

- **Kritischer Fund: Zeitumstellung im Oktober lässt `LocalDateTime`-Hochwassermarken rückwärts laufen.** Europe/Berlin-Wandzeit ist bei der Winterzeit-Rückstellung (letzter Sonntag im Oktober) NICHT monoton — 02:00-03:00 läuft zweimal. Ein Lauf, dessen `since`/`until` über den Sprung fällt, sieht `since=02:59 > until=02:00`, das Fenster ist leer, aber `lastChecked` wird trotzdem auf 02:00 zurückgesetzt → jede Erinnerung zwischen 02:00 (exkl.) und 03:00 feuert in der wiederholten Stunde ein zweites Mal. **Fix:** `lastChecked` als `Instant` halten (in realer Zeit garantiert monoton), Vorkommen-Wandzeit je Aufruf über `occ.getOccurrenceDate().atTime(time).atZone(clock.getZone()).toInstant()` umrechnen. Bei der mehrdeutigen Stunde löst Java `LocalDateTime.atZone()` bewusst auf die **frühere** (Sommerzeit-)Instant auf — die ist nach dem ersten Feuern bereits "verbraucht" und liegt beim zweiten Durchlauf durch dieselbe Wanduhrzeit vor dem neuen Fensteranfang, feuert also nicht erneut. Kommentar dazu direkt am Feld, nicht nur im Commit — sonst fliegt die Begründung beim nächsten Refactoring raus.
- **NPE-Lücke:** `reminderTime()` warf `atTime(null)` für einen Nicht-Ganztagstermin ohne Startzeit (API schließt das aus, aber Altdaten/manueller DB-Eingriff nicht). Schwerwiegender als bei `CalendarEventService.isAlreadyOver` (das denselben Fall bereits defensiv abfängt), weil der Wurf hier **vor** dem `EntityStateService`-Aufruf passiert, die Schleife abreißt und wegen des unbedingt fortschreitenden `lastChecked` alle weiteren fälligen Termine des Laufs verloren gehen. Fix: fehlende Startzeit wie ganztägig behandeln (Fallback auf `ALL_DAY_REMINDER_TIME`).
- **Test-Lücke:** Alle 3 Erstversion-Tests riefen nur `fireRemindersBetween` direkt auf — der eigentliche `@Scheduled`-Einstiegspunkt (`checkDueReminders`) war ungetestet. Ergänzt: 2 aufeinanderfolgende Läufe mit fortschreitender Uhr (lückenlos, keine Doppelung/kein Ausfall), Exception in `getOccurrences` reißt den Lauf nicht und `lastChecked` schreitet trotzdem fort, mehrere fällige Termine im selben Fenster feuern alle, fehlende Startzeit stürzt nicht ab, und ein expliziter DST-Regressionstest über die Oktober-Rückstellung. Dafür eine kleine testlokale `MutableClock extends Clock` (überschreibt nur `instant()`/`getZone()`/`withZone()`, mit `advanceTo(Instant)`) — für Szenarien, die eine fortschreitende Uhr über mehrere `checkDueReminders()`-Aufrufe brauchen, reicht `Clock.fixed` nicht.
- Ergänzte Kommentare (Review-Punkt 4, kein Codeeffekt): am `lastChecked`-Feld/`@Scheduled`, warum Korrektheit ohne Synchronisierung auf `fixedDelay`s Nicht-Überlappungsgarantie beruht (mit `fixedRate`/`@Async` wäre `lastChecked` ein Datenrennen); an `fireRemindersBetween`, warum bewusst das bestehende (volle-Tabelle-ladende) `getOccurrences` wiederverwendet wird statt einer engeren Abfrage.
- Nach dem Fix: 8/8 `CalendarReminderSchedulerTest`, volle Suite 653 Tests mit den immer gleichen 3 Umgebungsfehlern.
- **Lesson für jeden künftigen `@Scheduled`-Service mit einer "zuletzt geprüft"-Hochwassermarke:** niemals `LocalDateTime`/Wandzeit als Vergleichsbasis für ein fortschreitendes Zeitfenster verwenden, wenn die Zone DST hat — nur `Instant` (oder `OffsetDateTime` mit fixem Offset) ist garantiert monoton. Diese Klasse von Bug taucht nur zweimal im Jahr auf (und nur in der betroffenen Stunde), ist also im normalen Testen/Betrieb unsichtbar, bis es zu spät ist — bei jedem neuen zeitfensterbasierten Scheduler explizit einen DST-Test wie oben einplanen, nicht erst wenn die Review danach fragt.

## Gesamt-Review-Fix: UNTIL vor Startdatum wurde nie abgelehnt (post-Task 15)

`CalendarEventService.validate()` reichte die RRULE nur an `expansionService.validate(String)` (Syntax-Check) weiter — das Startdatum war dort unbekannt, also erzeugte ein `UNTIL` vor dem Start eine Serie, die 201 zurückgab, aber nie ein Vorkommen liefert (unsichtbar in Monatsraster, Hub, Erinnerungen).

- **Fix:** `RecurrenceExpansionService.hasAnyOccurrence(rrule, seriesStart)` neu ergänzt — fragt direkt `rule.iterator(toDateTime(seriesStart)).hasNext()`, **nicht** ein Zeitfenster (z.B. `expand(..., start, start.plusYears(1))` leer?). Grund: eine gültige Regel kann einen späten ersten Treffer haben (`FREQ=YEARLY;BYMONTH=2;BYMONTHDAY=29` ab einem Nicht-Schaltjahr trifft erst 2 Jahre später) und wäre bei einer Fenster-Prüfung fälschlich als "leer" erkannt worden. `CalendarEventService.validate()` ruft das nach dem bestehenden Syntax-Check auf und wirft 400 bei `false`.
- **Verifiziert per Wegwerf-Probe gegen die echte 0.17.1-Jar** (nicht nur angenommen): `iterator(start).hasNext()` liefert korrekt `false`, wenn `UNTIL` vor `start` liegt (mit floating `DateTime`, kein `Z`-Suffix — Frontend erzeugt `UNTIL` immer als reines Datum `YYYYMMDD`, matcht floating `DTSTART`). Für `FREQ=YEARLY;BYMONTH=2;BYMONTHDAY=29` ab 2026 liefert `hasNext()` sofort `true` (erster Treffer 2028), kein Hängenbleiben.
- **Überraschender Fund:** `RecurrenceRule.iterator(DateTime)` wirft bereits bei der **Konstruktion** eine `IllegalArgumentException("too many filtered recurrence instances")` für eine syntaktisch gültige, aber nie erfüllbare Regel (z.B. `FREQ=YEARLY;BYMONTH=2;BYMONTHDAY=30` — 30. Februar existiert nie). Das passiert *nach* `parse()` (der nur den `new RecurrenceRule(rrule)`-Konstruktor abfängt), also braucht `hasAnyOccurrence` einen eigenen `try/catch (IllegalArgumentException)` um den `.iterator(...)`-Aufruf, der `false` zurückgibt statt die Exception durchzureichen.
- Frontend: `buildRrule` (`frontend/src/app/shared/rrule.util.ts`) bekam dieselbe Prüfung als Sofortfeedback (ISO-Datumsstrings `YYYY-MM-DD` sind lexikografisch vergleichbar, kein Parsing nötig) — passt sauber neben die bestehende "fehlendes untilDate"-Prüfung in derselben Funktion. Der "Erweitert"-Modus (Roh-RRULE-Text) bleibt bewusst ungeprüft, wie auch sonst jede andere Syntaxfrage dort nur vom Backend gefangen wird.
- Tests: 3 neue in `RecurrenceExpansionServiceTest` (UNTIL-vor-Start, normale Regel, Feb-29-Spät-Treffer), 2 neue in `CalendarEventServiceTest`, 2 neue in `rrule.util.spec.ts`. Volle Suite danach: Backend 658 Tests (0 Failures, 3 bekannte Env-Errors), Frontend 252 Tests (4 bekannte Vorbestehende Fails, Rest grün).
