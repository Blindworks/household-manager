Tasks 10-12 of the usermanagement plan (`docs/superpowers/plans/2026-07-25-user-management.md`) were implemented verbatim from the plan's Soll-Code, in the `feature/user-management` worktree. Commits: `0d70aaf` (AppUserService + AdminUserInitializer), `e2128d9` (Nuki KIOSK-only-lock rule on `NukiController.executeAction`, now takes an `Authentication` param), `1c4802c` (UserAdminController/ServiceTokenAdminController/AuditLogController under `/v1/admin/**`).

**One deviation from the plan's literal test code:** the plan's `AppUserServiceTest` (Task 10) stubs `repository.save(any())` once in `@BeforeEach` for reuse across all test methods. With JUnit5's per-method test instantiation, Mockito's `MockitoExtension` (default `Strictness.STRICT_STUBS`) checks stub usage per test method, not per class — so the 3 tests that throw before reaching `save()` (`createMitVergebenemNamenWirftDuplicate`, `letzterAktiverAdminKannNichtDeaktiviertOderDegradiertWerden`, `bootstrapTutNichtsWennNutzerExistieren`) failed with `UnnecessaryStubbingException`. Fixed by wrapping that one `@BeforeEach` stub in `lenient()` — no other change needed, and it doesn't weaken the assertions that matter (the save-stub's behavior when actually invoked is still verified by the tests that do reach it).

**Takeaway for future plan-provided test code in this project:** if a plan test class defines a shared "happy path" mock stub in `@BeforeEach` that not all test methods will exercise (e.g. guard-clause/early-return tests), expect `UnnecessaryStubbingException` under this project's strict Mockito setup and pre-emptively mark that stub `lenient()` rather than treating the resulting failure as a real implementation bug — the plan's example code assumed a class-level/lenient stubbing session that JUnit5 per-method instantiation doesn't provide by default.

No other deviations: `NukiControllerKioskRuleTest` and the Task 12 admin controllers matched the plan's code and compiled/passed unchanged. Existing Nuki tests (`NukiLockServiceTest`, `NukiApiClientTest`, `NukiPollingServiceTest`) and Telegram/flow-engine callers of `NukiLockService.executeAction` (not the controller) were unaffected by the controller signature change, verified by running them alongside.

**Follow-up from quality review (commit `4abcd96`):** added plain-Mockito unit tests (no MockMvc, same style as `NukiControllerKioskRuleTest` — construct the controller manually via a `controller()` factory method rather than `@InjectMocks`, since these controllers have two collaborators and the pattern reads clearer) for `UserAdminController`, `ServiceTokenAdminController`, `AuditLogController`: mapping correctness, exact audit-record args (including that a service-layer exception short-circuits before any audit call — `verifyNoInteractions(auditService)`), and that `user.set-password`/`token.create` audit details never contain the raw password/token plaintext. Also added the project's "Bewusster Trade-off" comment convention at two spots in `AppUserService`: `countOtherActiveAdmins` (last-admin guard isn't race-free, accepted at household scale) and `update` (self-degrade/self-disable is allowed if another active admin exists; own session loses access via `DisabledUserSessionFilter` or on next request, not instantly).
