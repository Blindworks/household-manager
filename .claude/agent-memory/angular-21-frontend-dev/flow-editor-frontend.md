# Flow Editor (Stufe 3b) — Frontend

- Models: `frontend/src/app/models/flow.model.ts` — `FlowNode`, `FlowWire`, `FlowDefinition` (the flow JSON, mirrors backend), `FlowSummary`/`FlowDetail` (list vs. detail DTOs, detail adds `draftDefinition`/`deployedDefinition`/`createdAt`), `NodeType`/`NodeFieldDescriptor` (node palette + config-panel schema from `/api/v1/flows/node-types`), `ValidationResult` (`errors`/`warnings`), `DebugEntry`.
- Service: `frontend/src/app/services/flow.service.ts` — REST client for `/api/v1/flows`, `providedIn: 'root'`, `inject(HttpClient)` per `entity-state.service.ts` convention. Key gotcha: `POST /flows/{id}/deploy` returns the same `{errors, warnings}` body shape on both 200 (valid) and 400 (invalid) — the service normalizes both into `Observable<ValidationResult>` via `catchError`. Don't just do `of(err.error as ValidationResult)` — on real network errors (timeout/DNS/status 0) `err.error` is `null`/`ProgressEvent`, not a ValidationResult, and callers reading `result.errors` would crash. Guard with `(err?.error && Array.isArray(err.error.errors)) ? err.error : { errors: ['Netzwerkfehler beim Deploy.'], warnings: [] }` so `deploy()` always returns a usable object. Caught in code review after the initial B2 implementation (commit fc52467), fixed in 785ee56. `importFlow(payload: unknown): Observable<FlowDetail>` posts to `/api/v1/flows/import`.
- Consumed starting at ED-B3 (`FlowGraphMapper`) onward — treat these two files as the stable contract for the rest of the flow-editor components (palette, config panel, canvas, debug panel).
- ED-B4 (flow list page): `frontend/src/app/pages/flows/flow-list.component.ts/.html/.scss/.spec.ts` — signal-based standalone page (`flows = signal<FlowSummary[]>([])`), loads via `FlowService.getFlows()` in `ngOnInit`, `createFlow()`/`toggleEnabled()`/`deleteFlow()` all re-`reload()` after their service call resolves. Routed at `/flows` in `app.routes.ts` (lazy `loadComponent`) and linked from `HeaderComponent.navLinks` (label "Automatisierungen", no umlauts issue since word has none). The `/flows/:id` editor route is deliberately NOT added yet — `FlowEditorComponent` doesn't exist until ED-B9; adding the route earlier would break the build.
- ED-B5 (picker widgets, commit 2cb1aa9): `frontend/src/app/pages/flows/pickers/{entity,device,alexa-device}-picker.component.ts/.html` (+ `entity-picker.component.spec.ts`, TDD-verified: red on missing module, 3/3 green after impl). Shared shape: `value = input<T>()` signal-input (not `@Input()`) so tests can `fixture.componentRef.setInput('value', ...)` before first `detectChanges()`; `@Output() valueChange = new EventEmitter<T>()` (plain EventEmitter, not `output()`, to match the rest of this codebase's event-emission style); `options = signal<TModel[]>([])` loaded in `ngOnInit` via the existing services (`EntityStateService.getEntities()`, `SmartDeviceService.getAllDevices()`, `AlexaService.getDevices()`) — no new services created. Core UX requirement: an unknown/stale selected value (entity or device deleted server-side) must NOT be silently dropped — `displayLabel` computed signal falls back to `` `nicht gefunden: ${v}` `` and the template shows it via a `.picker__missing` span, checked with `.startsWith('nicht gefunden')`. Value-type mapping: entity picker value = `entityId` (string), device picker value = `id` (number, template binds `value() ?? ''` — safe because `??` only catches null/undefined, so device id `0` still renders/selects correctly, unlike `||`), Alexa picker is multi-select = `string[]` of `serialNumber`s via checkboxes (`Set`-based toggle, emits `[...next]`). No `.scss` files created for these three (task scope only asked for `.ts`+`.html`); CSS classes (`.picker`, `.picker__missing`, `.picker--multi`, `.picker__check`) are unstyled placeholders — B6 (NodeConfigPanel) or a later polish pass should add styles when these get embedded, or add global styles. `CommonModule` imported per given spec even though only built-in `@if`/`@for` control flow is used (no actual CommonModule directives needed) — kept for consistency with the task's exact prescribed code rather than trimming.
- ED-B6 (config panel, commit 40aa683): `frontend/src/app/pages/flows/node-config-panel.component.ts/.html/.scss/.spec.ts` — schema-driven form, `node = input<CanvasNode>()` + `nodeType = input<NodeType>()`, renders one `.config-field` div per `NodeType.fields[]` entry with an `@switch (field.type)` picking the widget: ENUM→`<select>`, NUMBER→`<input type="number">`, ENTITY_REF/DEVICE_REF/ALEXA_DEVICE_LIST→the B5 pickers, default→text input. `setField(key, value)` is non-mutating (spreads `node().config` into a new object) and emits the *whole* new config via `@Output() configChange` — the editor (B9) owns applying it back onto the node, this component never touches `node()` in place. `isRequired(key)` just reads the field descriptor's `required` flag for the `*` marker; no actual validation/enforcement lives here. Template guards `@if (node() && nodeType())` then uses `nodeType()!.type` — signal calls don't narrow across separate invocations in TS, hence the non-null assertion after the guard (recurring pattern, not a smell). Picker value bindings need `$any(fieldValue(field.key))` casts since `fieldValue()` returns `unknown` (config bag is `Record<string, unknown>`) but pickers expect concrete `string`/`number`/`string[]` inputs. This is the first place all three B5 pickers get imported together, so this file's `ng build --configuration production` is the first real compile-check of `device-picker`/`alexa-device-picker` (previously only `entity-picker` had a spec/consumer) — build passed clean. `.scss` here also backfills the previously-unstyled `.picker`/`.picker__missing`/`.picker--multi`/`.picker__check` classes from B5 since this is the first place they're actually embedded in a page.
- ED-B8 (canvas, commit 4c99bce): `frontend/src/app/pages/flows/flow-canvas.component.ts/.html/.scss` — the only place besides `FlowGraphMapper` that imports `@foblex/flow` directly; see [[foblex-flow]] for the full library gotchas (minimap placement, connection-SVG-invisible fix applied `::ng-deep` component-scoped, theme wiring deliberately deferred to B9, delete UX via `fDragBlocker` button + `fConnectionContent` mid-connection button, connector-id scheme `nodeId::in` / `nodeId::out::<port>`). **General gotcha worth generalizing to any unwired standalone component**: `ng build` silently skips type-checking components with zero consumers — verify by temporarily wiring into `app.routes.ts`, building, then reverting (confirmed clean revert via `git diff`).
- ED-B10 (debug panel, commit 704cf13): `frontend/src/app/pages/flows/debug-panel.component.ts/.html/.scss/.spec.ts` — polls `FlowService.getDebug(flowId, nodeId)` every 2s (`interval(2000).pipe(startWith(0), switchMap(...))`) for every `debug`-type `CanvasNode`, aggregated via `forkJoin` and sorted by `timestamp`. Gated by two signal inputs, `active` (tab visible) and `deployed`; only polls when both true. Implementation pattern worth reusing for any future "poll while visible" panel: an `effect()` in the constructor computes `shouldPoll = active() && deployed()`, unconditionally calls `this.sub?.unsubscribe()` first, then early-returns if `!shouldPoll` — this both stops polling immediately when either flag flips false AND makes the effect *not* reactive to `nodes()`/`flowId()` while idle (they're only read after the early-return, so untouched signal reads don't count as dependencies — confirmed correct/intentional, not a bug). `takeUntilDestroyed(this.destroyRef)` works fine even though the `.pipe()` call happens inside the `effect()` callback (not the constructor's synchronous injection-context body) — because `DestroyRef` was captured via `inject()` in a field initializer and passed explicitly as an argument, `takeUntilDestroyed` doesn't need to run in an active injection context. No `HttpClient`/`TestBed` timing workarounds were needed — spied `FlowService.getDebug` returning `of([...])`, `fakeAsync` + `tick(0)`/`tick(2000)` + `discardPeriodicTasks()` was sufficient; both tests (polls-when-active-and-deployed, no-poll-when-not-deployed) passed on the very first implementation attempt.
- ED-B9 (editor orchestration): `frontend/src/app/pages/flows/flow-editor.component.ts/.html/.scss/.spec.ts` — wires `NodePaletteComponent`, `FlowCanvasComponent`, `NodeConfigPanelComponent`, `DebugPanelComponent` together. `ActivatedRoute` is read synchronously via `this.route.snapshot.paramMap.get('id')` in a field initializer (not `ngOnInit`), so tests must provide `{ provide: ActivatedRoute, useValue: { snapshot: { paramMap: { get: () => '1' } } } }` — a plain object stub is enough, no `RouterTestingModule`/`convertToParamMap` needed. Dirty-tracking is snapshot-diff based, not a mutation flag: `savedSnapshot` stores the serialized `FlowDefinition` JSON right after load/save/deploy, and every mutating handler (`addNode`, `onNodeMoved`, `onConnectionCreated/Deleted`, `onNodeDeleted`, `onConfigChange`) calls a shared `markDirty()` that re-serializes and string-compares against `savedSnapshot` — this makes `dirty()` correctly flip back to `false` if a user's edit round-trips to the same content, and avoids missing a dirty transition if a handler forgets to explicitly set a flag. `deploy()` chains `saveDraft(...).subscribe(() => ... this.flowService.deploy(...))` — deploy always saves first, so the deployed definition can never be older than the last edit. Theme registration (the B8-deferred task): added `"node_modules/@foblex/flow/styles/default.scss"` as the *first* entry (before `src/styles.scss`) in **both** `angular.json` `architect.build.options.styles` and `architect.test.options.styles` arrays — this project's `angular.json` has a single flat `styles` array per target (no per-configuration override), so one edit per target is enough, no need to touch `configurations.production`/`development`. Confirmed resolved: `ng build --configuration production` succeeded and `styles-*.css` grew to include the foblex theme; Karma also picked it up (no FF1002-unrelated errors, only the expected pre-existing zero-height warning from `f-flow` in jsdom-less headless Chrome, which is cosmetic-only and doesn't fail tests). Added the `flows/:id` route (deferred since B4) right after the `flows` list route in `app.routes.ts`, lazy-loading `FlowEditorComponent` — this was the first build that actually type-checked the full canvas/palette/config/debug component tree together (lazy routes are otherwise skipped by `ng build`'s type checker, per the ED-B8 gotcha above), and it passed clean.

Added `frontend/src/app/pages/flows/unsaved-changes.guard.ts`, a functional `CanDeactivateFn<FlowEditorComponent>` reading the component's already-public `dirty()` signal and gating navigation on `confirm(...)`; wired via `canDeactivate: [unsavedChangesGuard]` on the `flows/:id` route in `app.routes.ts`. `FlowListComponent.deleteFlow` now confirms before calling the service; `getFlows`/`createFlow`/`setEnabled`/`deleteFlow` all got an `error` signal + `.flow-list-page__error` banner, copying the `entities.component.ts` pattern (`error.set(err.message)`) exactly — this is the established error-signal convention in this codebase, reuse it verbatim for any other list/CRUD page that still swallows errors. Cosmetic-only, no functional risk: palette item `cursor: grab` → `cursor: pointer` (no real HTML5 drag exists yet, `grab` was misleading); added a `label(type)` lookup map in `NodePaletteComponent` for readable German button text, falling back to the raw `type` for anything not in the map (existing palette spec asserts `.length` per group, not text, so it stayed green untouched); `debug-panel.component.html`'s `@for` track expression dropped an unnecessary `$any(e).label` cast now that `DebugEntry.label` is a real typed field (was leftover from before the model existed).

  - **Testing gotcha confirmed**: adding a `confirm()` call inside a component method that an existing spec already exercises (`flow-list.component.spec.ts`'s "deletes a flow and reloads") requires `spyOn(window, 'confirm').and.returnValue(true)` in that `it()` block — Karma/Jasmine's `window` is the real browser window in ChromeHeadless, so an un-stubbed `confirm()` genuinely blocks/auto-dismisses and breaks the test rather than being a no-op.
- ED-Import (flow-list import button, commit 54f4eec): `frontend/src/app/pages/flows/flow-list.component.ts/.html/.scss/.spec.ts` — hidden `<input type="file" hidden>` triggered by a visible button's `(click)="importFile.click()"` (template ref var, no ViewChild needed). Handler resets `input.value = ''` synchronously right after reading `input.files?.[0]` (before the async `file.text().then(...)`) so re-selecting the identical file still fires `change` next time. `JSON.parse` wrapped in try/catch with an early return on failure — standard "guard before network call" shape for any future file-import feature in this codebase. Error display distinguishes `err.message` (client-side, e.g. plain HttpErrorResponse from services without a structured body) vs `err.error?.message` (reads the backend's structured `ErrorResponse.message` on a 400 from `FlowService.importFlow`) — pick based on what the failing call actually returns, not by copy-pasting one blindly. Spec tests call the private `importFromText` method via bracket-index access (`fixture.componentInstance['importFromText'](...)`) — a legitimate, already-established pattern in this codebase for testing private handlers without exposing them publicly.
